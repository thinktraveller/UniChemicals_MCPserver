# 项目目标文档

## 项目愿景
[草案，基于 QA-R001]：将 pubchempy-mcp-server 整理成一个结构清晰、可正常打包发布、工具语义化命名，并覆盖更丰富 PubChem 数据类型（3D 结构/光谱/描述符等）的 MCP 服务器。

## 背景与动机
用户希望对 pubchempy-mcp-server（基于 PubChemPy 的 MCP 服务器）的源码进行整理，并增加新功能。现状痛点：单文件结构导致工具高度重复、打包配置与源码目录不一致导致无法正常构建、现有工具族覆盖不足。

## 核心目标
[草案，基于 QA-R001 + QA-R002]
1. 修正打包配置，使项目能够正常构建（`uv build`）并可发布。
2. 重构代码结构，消除工具函数的高度重复，提升可维护性。
3. 补充现有工具族（如批量查询等能力）。
4. 新增 3D 结构（conformer）、光谱、描述符等数据类型工具。
5. MCP 工具采用语义化命名：`{数据库}_{动作}_{实体}_by_{标识符}`（例：`pubchem_search_compound_by_cid`），并为未来接入其他数据库预留扩展空间。

## 范围界定
### 包含
[草案，基于 QA-R001]
- 打包配置修正
- 代码结构整理/重构
- 现有工具族补充
- 新增 3D 结构 / 光谱 / 描述符类工具
- MCP 工具语义化命名

### 排除
- 下载类工具：现有 6 个 `download_by_*` 工具全部移除，且不新增。

## 约束条件
[草案，基于 QA-R001 + QA-R002]
- 不做下载工具（现有 `download_by_*` 全部移除）。
- MCP 工具采用语义化命名：`{数据库}_{动作}_{实体}_by_{标识符}`（例：`pubchem_search_compound_by_cid`）。
- 命名需为未来接入其他数据库（如 ChEMBL、DrugBank 等）留出扩展空间。
- 时间无紧迫要求。

### QA-R002：下载工具去留、命名兼容策略与成功标准
<!-- GOAL-QA-R002-START -->
- **提问时间**：2026-08-06 14:55
- **提问目的**：QA-R001 的回答中，有两处直接影响范围界定与兼容性的关键点需要确认（现有下载工具怎么处理、语义化命名是否重命名现有工具），同时补齐成功标准与时间约束。
- **问题列表**
  1. 现有 6 个 `download_by_*` 工具怎么处理？（a. 全部移除；b. 保留不动但不再新增；c. 保留并重命名成语义化名称）

  3. 这次改造的「成功」如何判断？有没有时间预期？（例如：必须能 `uv build` 成功并在本地跑通；预计何时交付）
- **用户回答**
  1. 现有 6 个 `download_by_*` 工具全部移除。
  2. 采用 `pubchem_search_compound_by_cid` 风格：命名必须包含来自哪个数据库（pubchem）、搜索什么（compound）、依靠什么搜索（cid）；考虑后续可能接入其他数据库。

  - 命名规范确立为 `{数据库}_{动作}_{实体}_by_{标识符}`，预留多数据库扩展。
  - 成功标准明确：可构建 + 可通过 uvx 远程运行。
